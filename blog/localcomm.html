localcomm: finding and messaging devices on a LAN in async Rust

Started February 2026 · Work in progress

RustTokiomDNSTCP

Two laptops on the same Wi-Fi are a few milliseconds apart, yet sending a note between them usually means a round trip through someone's cloud. localcomm is a small command-line tool that lets machines on a local network find each other and exchange messages directly, with no server and no configuration.

Background

I wanted a project that would make me learn async Rust properly, and networking is where async earns its keep. The problem also has a nice first obstacle: before two machines can talk, one has to learn the other's address. Typing IP addresses is exactly the kind of setup I wanted to avoid.

The standard answer is mDNS with DNS-SD, the mechanism behind printer discovery and Chromecast device lists. A device announces a named service on the local network, and anyone browsing for that service type gets its address and port.

Approach

Discovery

A server registers the service type _localcomm._tcp.local. with its port and a few TXT properties (device name, version). A client browses for that type until a timeout expires and collects every service that resolves. I used the mdns-sd crate for the protocol itself.

Wire format

Messages are JSON objects, one per line:

{"id":"5f0c3a8e-...","type":"text","from":"machine-b",
 "to":"192.168.1.42:8080","content":"hello","timestamp":1790479705,"metadata":{}}

Newline-delimited JSON is not the most compact choice, but it is easy to debug: you can talk to the server with nc and read the traffic by eye. The type field already covers file chunks, heartbeats and acknowledgements, so the format will not need to change as those features arrive.

Concurrency

The server has one accept loop. Each accepted connection gets its own Tokio task, which reads lines, parses them, and sends each message into an mpsc channel. A single handler at the other end of the channel prints messages in order.

The appeal of this shape is that no state is shared between connections, so there are no locks. Every connection owns its socket and its buffer, and the channel is the only meeting point.

File transfer

The transfer path sends a small header (file name and size) and then the file in 64 KB chunks. Both sides feed the bytes through SHA-256 as they stream, so a large file never has to fit in memory.

What I learned

  • Framing is a real decision. TCP delivers a stream of bytes, not messages. Line-delimiting works for JSON text but not for raw file bytes, which is why the transfer path uses a header with an explicit length.
  • An unbounded channel has no backpressure. If senders outpace the handler, memory grows. A bounded channel would make a fast sender wait, which is the behaviour I want.
  • Ownership shapes the design. Moving each socket into its own task was the path of least resistance in Rust, and it turned out to be the cleanest design too.

Next

  • Wire transfer into the CLI, send the checksum to the receiver, and verify it.
  • Add heartbeats and acknowledgements so a sender knows a message arrived.
  • Address devices by name, resolved through mDNS, instead of by host:port.
  • Encrypt the traffic. It is currently unencrypted and unauthenticated, so it should only be used on a network you trust.
