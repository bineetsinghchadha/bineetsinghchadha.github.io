An on-chain audit trail for AI agents that delegate to each other

Project period: Spring 2026

SolidityHardhatPythonLangChainOllama

When one AI agent hands a task to another, and that agent hands part of it to a third, who authorized what? This project records every delegation and every action on a blockchain, and makes the contract itself refuse any delegation that grants more authority than the delegator holds.

Background

Multi-agent systems split work: a manager agent plans, worker agents write code, a tester checks it. If something goes wrong, you want to reconstruct the chain of responsibility. Application logs can do that, but only if you trust whoever runs the log.

The paper Intelligent AI Delegation (Tomasev et al., 2026) proposes Delegation Capability Tokens (DCTs): a token that records who delegated which scope of authority to whom. I implemented the idea as a smart contract and connected it to a working agent pipeline.

What it does

Human principal
   |  mints a MANAGE token
   v
Manager agent  -- splits the task in two
   |-- mints a CODE token --> Coder A  (writes module_a.py)
   |-- mints a CODE token --> Coder B  (writes module_b.py)
   |
   |  both finish; manager mints a TEST token
   v
Tester agent  -- runs pytest, logs pass or fail on-chain

The two coder agents run in parallel. Every delegation, action and result is written to the chain, and the full history can be rebuilt from any token by walking up to the root.

Approach

The contract

DelegationRegistry.sol stores each token with its parent, delegator, delegatee, scope, task description, expiry, and revoked and completed flags. Its main functions:

FunctionPurpose
mintRootThe human issues the root MANAGE token
delegateA token holder issues a child token with a narrower scope
recordActionA holder logs an action against its own active token
complete, revokeClose a token normally, or withdraw it
getChainReturn the delegation chain from a token up to the root

Scope as an ordered enum

Scope is an enum ordered from broadest to narrowest: MANAGE (0), CODE (1), TEST (2). That turns the central rule, that nobody can grant more authority than they hold, into one integer comparison inside delegate:

require(uint8(scope) > uint8(parent.scope), "Scope escalation denied");

Because the check lives in the contract, an agent that is buggy or compromised cannot talk its way past it. The transaction simply reverts. The same function also rejects delegation from tokens that are revoked, completed or expired.

The agents

The agents are LangChain programs running on a local model through Ollama, so the whole pipeline works without API keys. Each agent has its own wallet. A small Python client wraps the contract calls, and the agents call it at each step: when they receive a task, delegate, write code, or report a test result.

Running it

Locally it runs against a Hardhat node. It also deploys to the Sepolia test network, and a browser dashboard reads the delegation tree and the action log straight from the chain.

Design decisions

  • Why a blockchain and not a database? The agents in a pipeline may belong to different operators who do not trust each other. A database needs a trusted owner. A public ledger does not, and nobody can rewrite it afterwards.
  • Why enforce scope on-chain? An application-level check protects only the applications that remember to run it. A contract-level check applies to every caller.
  • Why fan-out delegation? Two parallel coders show that one parent can hold several independent child tokens, each with its own action log and completion state.

Limits

  • Cost and latency. Every logged action is a transaction. On a public chain that costs gas and takes seconds, so a chatty agent would be expensive. Logging hashes of actions instead of full text would cut the cost.
  • The log proves what was recorded, not what happened. An agent could act without logging. Closing that gap needs the execution environment to require a valid token before it runs anything.
  • Three scopes are a demonstration. Real systems would need a richer permission model than a single ordered list.
