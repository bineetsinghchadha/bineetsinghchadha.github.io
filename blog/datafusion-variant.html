Writing a typed Variant getter for DataFusion

March 2026 · Fork of datafusion-contrib/datafusion-variant

RustApache DataFusionArrowParquet Variant

I wanted to understand how a query engine exposes a function to SQL, so I implemented one: variant_get_bool for the datafusion-variant crate. My branch was not merged, because the maintainers landed their own implementation a few days later. The exercise was still worth writing up.

Background

Variant is a binary encoding for semi-structured data, the kind you would otherwise store as a JSON string. It is part of the Parquet and Iceberg specifications and is supported by Spark and Databricks. Compared with JSON text, a query can jump to one field without parsing the whole document.

datafusion-variant adds Variant functions to Apache DataFusion, a query engine written in Rust, and aims to match the functions Spark offers. When I looked at it, variant_get_int had just been added and the boolean getter was missing.

What the function does

variant_get_bool(variant, path) returns the value at path as a SQL boolean.

select variant_get_bool(json_to_variant('{"name": "Alice", "active": true}'), 'active');
-- true

The edge cases are the real specification:

  • a boolean at the path is returned as it is;
  • a value of any other type (string, number, array, object) returns NULL;
  • a path that does not exist returns NULL.

Approach

In DataFusion a scalar function is a type that implements the ScalarUDFImpl trait. The trait asks for a name, a signature, a return type, and an invoke_with_args method that does the work.

  • Signature. Two arguments of any type, marked immutable so the planner knows the same input always gives the same output.
  • Return type. Always Boolean.
  • Invocation. The crate has a shared helper for typed getters that handles path lookup and the scalar-versus-array cases. My function supplies three small pieces: how to build a scalar result, how to build an Arrow BooleanArray from a column of results, and how to extract a boolean from a single Variant value.

That last piece is one line, because the Variant type already has an as_boolean accessor that returns None for non-booleans. Reusing the shared helper kept the function to the parts that are specific to booleans.

Tests

I wrote unit tests for true, false, a missing path and array inputs, plus a sqllogictest file. That format pairs SQL statements with their expected output, so the function is tested through the same path a user would take:

query B
select variant_get_bool(json_to_variant(json_str), 'active') from json_data;
----
true
false
NULL

What happened

I finished my branch on 21 March 2026. On 24 March the maintainers merged their own variant_get_bool, so mine was not needed.

What I learned

  • Claim the work first. The project tracks missing functions in an issue. A one-line comment saying "I'm taking this" would have avoided the duplicate effort.
  • Scalars and arrays are two paths. A function can be called with a constant or with a column, and it has to handle both. The shared helper hides this, and reading it taught me more than writing my own function did.
  • Null handling is most of the design. The happy path was one line. The decisions were all about what to return when the type or the path is wrong.
  • Small functions are a good way into a large codebase. I now know my way around the crate well enough to pick up something bigger.
